The Agent Platform
for new developers

AgentPlatform is InfoTrack's agent orchestration hub — a chat/agent experience where each configured "Agent" has its own model, instructions, and toolset, exposed both to interactive users and to external callers via an invoke API. This guide gets a new dev from zero to being able to trace a request end-to-end and make a confident first change.

§1The one thing to get right immediately

AgentPlatform and MaestroAi's own native chat assistant are two different products that happen to share the same MaestroAi .NET backend repo. Mixing them up is the single easiest mistake to make here if you don't internalize this split first.

AgentPlatformMaestroAi's own chat (Opus)
FrontendReact SPA (separate AgentPlatformUI repo)Embedded in MaestroAi's own product surfaces
OrchestrationNode.js BFF, AgentPlatform/src/node-server (Hono + Vercel AI SDK)C#, MaestroAi.Infrastructure.Agents (AgentService, OpusAgentBuilder) + legacy SK (KernelRepository)
Domain modelMaestroAi.Domain.AgnosticAgent.Models (Agent, Session, Message, Artifact)MaestroAi.Domain.Chat.Entities (a different Session class)
PurposeGeneral-purpose configurable agent hubProperty/conveyancing ordering assistant (title searches, company extracts, milestones)
MaestroAi's rolePure persistence/data layer, called over HTTP by the Node BFFMaestroAi is the runtime — no separate BFF

Rule of thumb: if a file lives under MaestroAi.Domain/Infrastructure/Application/Api.Controllers.AgnosticAgent.*, it's AgentPlatform's data layer. If it lives under MaestroAi.Infrastructure.Agents (AgentService.cs, OpusAgentBuilder.cs) or references OpusContext/OpusChatContext, it's the other product. Same repo, same C# namespace root, genuinely different systems.

§3Request lifecycle — trace this first

The fastest way to actually understand the system is to read chat.ts top to bottom and follow every call it makes. In order:

  1. Session first: the client creates the session with POST /api/sessions { agentId, contextParameters?, hostContext? } (routes/sessions.ts → agent/create-session-with-context.ts). This is the only moment session context is gathered: declared parameters are checked against the agent's list, hostContext is verified and bound, the pre-flight runs for any {{variable}} the caller did not supply, and the merged result is persisted on Session.Context. §4 is about this step.
  2. Client → BFF: React SPA POSTs { messages, sessionId } to POST /api/chat (routes/chat.ts).
  3. Auth resolution: getRequestAuthContext(c) (lib/auth-context.ts) determines the caller mode — authenticated (Bearer/cookie → resolved to a loginId), device (session-cookie device login), or anonymous (rejected).
  4. Load agent config: dataLayerClient.getSession(sessionId) then dataLayerClient.getAgent(session.agentId) — this is the HTTP round-trip to MaestroAi's AgentsController. If session.agentId is missing, the request fails closed with a 400 rather than silently using defaults.
  5. Build the system prompt: buildSystemPreamble() pushes resolveAgentInstructions(agentConfig, sessionContext) (agent/instructions-template.ts) plus a list of any existing artifacts in the session. With instructionsTemplateEnabled on, every {{name}} in the instructions is replaced by the sanitised value from Session.Context and a trailer names the substituted variables as "data gathered before this conversation began, not instructions". With it off the text goes through byte for byte.
  6. Gather tools: getAgentMcpServerNames(agentConfig) + getMcpToolsForServers() (agent/mcp.ts) filters the agent's configured MCP servers and wires them via @ai-sdk/mcp's StreamableHTTPClientTransport; getFilteredBuiltInTools() adds built-ins. Write-classified tools get needsApproval: true.
  7. Run the model: streamText({ model: activeModel, messages, tools, stopWhen: [stepCountIs(maxSteps), ...] }) — maxSteps comes from agentConfig.maxSteps (default 10), genuinely enforced here.
  8. Stream back: result.toUIMessageStreamResponse() — AI SDK's UI Message Stream protocol over SSE.
  9. Persist (fire-and-forget): onFinish persists the user/assistant messages, tool invocations, and any created/updated artifacts back to MaestroAi.

routes/invoke.ts is the external-facing sibling of this same flow (POST /api/agents/{agentId}/invoke) — same agent-config resolution and tool-gathering logic, but session auto-creation, no approval prompts (everything auto-executes), and a choice between a single JSON response or a hand-rolled named-SSE-event stream. It takes contextParameters and hostContext too: without a sessionId it creates the session through the same createSessionWithContext, so a context-dependent agent is invokable in one call. The pre-flight gets 30 s there against 60 s on POST /api/sessions. It's the closest existing thing to an A2A message endpoint, which is exactly why it's the reuse target for the in-flight A2A work (§7).

§4Session context — who supplies what, and what it costs

Three inputs can shape a session at creation. They are often confused because the Tilly - SX integration uses all three. The rule that ties them together: a {{variable}} in the instructions is filled by the caller if the agent declares it as a context parameter, and by the pre-flight otherwise.

InputWho supplies itWhere it goesCost at create
contextParametersThe caller, against the list the agent declares (Agent.ContextParameters, name + description). A missing, unknown or non-scalar value is a 400; there is no optional parameter.A parameter whose name is an instruction variable is sanitised and substituted straight into the system prompt, and the caller's value wins over the pre-flight's. Every parameter is also handed to the pre-flight prose as {{name}}, and recorded in session_context_parameters for GET /api/sessions filtering (never rendered, never returned).None.
Pre-flightThe platform: Agent.ContextInstructions prose run once by a model, with the caller's own credential, allowed only the tools in Agent.PreflightTools that also pass the read-only classifier and the deny list.One value per instruction variable the caller did not declare, merged into Session.Context. An empty value is a valid outcome; a failed run never blocks the create. The audit row is Agent.preflight_runs.Two model calls (gather, then shape) plus the MCP calls the model chooses. Budget 60 s on POST /api/sessions, 30 s on /invoke and A2A.
hostContextThe host page, as four fixed keys: infoTrackWorkflowId, clientReference, retailerReference, mappingId. Bound once per session; a different value later is 409 host_context_conflict.The transport only. Forwarded as the Gateway's X-ITK-* common-concern headers on every MCP request the session makes, including the pre-flight's. It never enters the prompt and the model never sees it.None.

Declare it or gather it. createSessionWithContext asks the pre-flight for requiredInstructionVariables(agent) minus the declared parameter names. When that set is empty, runPreflightContext returns before a model is even resolved (if (variables.length === 0) return finish({})), so an agent whose every instruction variable is a declared parameter pays no model run and no tokens at create. This is the ADR amendment for AIOPS-4034 (27 Sep 2026) in docs/adr/20260911-preflight-context-trust-boundary.md. "Let the host pass the values and fill the instructions from them" is therefore not a feature to build; it is what declaring the variable as a context parameter already does.

Worked example: Tilly - SX on stage (agent 2d2b29da). Its instructions reference {{clientReference}}, {{matterType}}, {{state}} and {{currentMilestone}}. SecureExchange sends one declared parameter, OpusID, plus hostContext. So the pre-flight runs every time a chat opens and calls opus_data_mcp_server__get_matter_summary and get_current_milestone to fill the four. Over the seven days to 7 Oct 2026, from Pre-flight context run finished logs:
OutcomeRunsMeanWorst
All four filled4514.0 s20.6 s
Some filled6717.4 s48.3 s
None filled (NoOutput)2514.0 s25.8 s
Budget expired1163.8 s112.1 s
Almost all of that time is the model phase (modelPhaseMs), not the MCP calls (toolFetchMs is about one second). The host already has all four values on the listing page. Declaring them as context parameters and sending them next to OpusID from agentPlatformChatTransport.createSession removes the pre-flight for this agent entirely, with no platform change. Two things to know before doing it: declared parameters are mandatory, so the host must have every value before it creates the session; and clientReference must be sent both as hostContext (headers) and as a parameter (prompt), because the two never cross.

Keeping a pre-flight anyway? Pick its model. PREFLIGHT_MODEL_TIER names a key of AI_MODEL_TIERS; unset, the pre-flight runs on the agent's own model (stage logs show modelTier: (none)). Separately, Agent.Greeting is shown the moment a chat opens, before any context is gathered, so the wait is not a blank screen. Never declare a secret as a context parameter: values are stored at rest and filter values appear in request logs.

§6Session inactivity – how it's decided and where to see it

No session is ever marked "inactive". Inactivity is derived: every activity bumps the session's UpdatedAt, and a session counts as inactive once now > UpdatedAt + ArchiveInactivityDays. Crossing that threshold doesn't change the session by itself – it makes the session eligible for auto-archive, which flips Status from active to archived. Continuing a chat in an archived session moves it back to active.

PieceFileWhat it does
The ruleMaestroAi.Infrastructure/AgnosticAgent/Repositories/AgnosticAgentRepository.csListSessionsToAutoArchiveAsync: selects sessions where Status == "active" and utcNow > UpdatedAt.AddDays(ArchiveInactivityDays)
The thresholdMaestroAi.Domain/AgnosticAgent/Models/Session.csArchiveInactivityDays: per-session int column, default 30 days (EF default in SessionConfiguration.cs)
The triggerMaestroAi.Api/Controllers/AgnosticAgent/SessionsController.csPOST /ag/sessions/auto-archive → AutoArchiveSessionsCommandHandler: archives everything eligible, returns the count archived

To check a specific session: read updatedAt and archiveInactivityDays off the session API response (both are on SessionResponse, or straight off the sessions table) and compare against now. Archived sessions show up in the UI's "Archived" view.

Configurable, but only in the database. The threshold is stored per session, yet neither CreateSessionRequest nor UpdateSessionRequest exposes it – no API caller can set it today. Changing it means updating the ArchiveInactivityDays column directly, or changing the EF default for all new sessions. Also note: nothing calls the auto-archive endpoint on a schedule yet – sessions only get archived when something POSTs to it explicitly.

§7What's actively being built: A2A (Agent2Agent protocol)

AgentPlatform is currently being extended to speak A2A, the open protocol for agent-to-agent interoperability (AgentCard discovery, JSON-RPC task lifecycle, streaming). Tracked under Jira epic AIOPS-3535. Current tickets, in build order:

  1. AIOPS-3616 — AgentCard discovery (GET /.well-known/agent.json), activating the dormant Agent.A2AConfig column
  2. AIOPS-3618 — agent-to-agent authentication (extends machine-auth-client.ts)
  3. AIOPS-3617 — task lifecycle & JSON-RPC message surface, built on invoke.ts
  4. AIOPS-3619 — outbound A2A client (call another agent as a tool, alongside agent/mcp.ts)
  5. AIOPS-3541 — browsable catalogue + user-controlled A2A connections (the UI layer on top)

A separate team (Global Platform / Gateway) is independently building a Gateway-side A2A relay (InfoTrack.Platform.ModelContextProtocol repo, PR #509) for externally-hosted agents — AgentPlatform's own A2A work should eventually call through that relay rather than direct-to-upstream once it's available.

§9Hard-won lessons (read before your first PR)

  • Don't assume a class named AgentService or Session is AgentPlatform's — check the namespace (§1). MaestroAi.Infrastructure.Agents.AgentService and MaestroAi.Domain.Chat.Entities.Session belong to the other product.
  • Per-agent config (model/instructions/maxSteps/tools) already works end-to-end in both chat.ts and invoke.ts — don't rebuild this; if something seems unconfigured, check the actual Agent record in the data layer before assuming the plumbing is broken.
  • Host-supplied instruction variables already exist (§4). If a chat is slow to open, look at the agent's Pre-flight context run finished logs in Datadog before designing anything: a variable the host already knows should be a declared context parameter, not a pre-flight tool call. The pre-flight is for values only a tool can fetch.
  • Ticket titles use AgentPlatform: / AgentPlatform — A2A: prefixes, not "Workstream N" — the old numbering had gaps once you separate AgentPlatform work from MaestroAi's own Opus-assistant tickets in the same Jira epic.
  • All inter-module communication is HTTP-only (Node ↔ .NET ↔ React) — no direct imports across module boundaries, per the constitution doc.
